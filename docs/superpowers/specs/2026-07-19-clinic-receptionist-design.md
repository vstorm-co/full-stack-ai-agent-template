# Clinic Receptionist Agent — Design Spec

**Date:** 2026-07-19
**Status:** Approved by user (brainstorming session)
**Approach:** Generate a project from this template, then customize it. The template repo itself is not modified.

## Summary

An AI receptionist for a small doctor's office, built on a project generated by
`fastapi-fullstack`. Patients interact via web chat and WhatsApp. The agent
handles appointment scheduling, office FAQs, message-taking with urgency triage,
and billing questions (informational + staff handoff only). It never gives
medical advice and never discusses PHI.

## Decisions (from brainstorming)

| Decision | Choice |
|---|---|
| Capabilities | Scheduling, FAQs, message-taking & triage, billing info + handoff |
| Channels | Web chat (built-in UI) + WhatsApp (Meta Cloud API webhook) |
| Schedule source of truth | In-app PostgreSQL database |
| Payments | Informational only; actual payment routed to staff/portal |
| PHI posture | No PHI in chat — generic info and scheduling requests only; personal details via staff follow-up |
| AI framework | PydanticAI |
| Build approach | Generate + customize (not a template preset, not standalone) |

## Foundation

Generate with:

```bash
fastapi-fullstack create clinic_receptionist \
  --ai-framework pydantic_ai --rag --database postgresql
```

(plus frontend enabled). This provides the FastAPI backend, Next.js chat UI,
auth, RAG pipeline, and admin panel. All work happens in the generated project.

## Agent

A PydanticAI receptionist with a purpose-built system prompt:

- Warm, professional front-desk persona.
- Hard scope limits: **never gives medical advice, never discusses PHI.**
- Works with anonymous/lightly-identified visitors; anything personal becomes a
  structured staff handoff via `take_message`.

### Tools

Replaces the template's generic tools (web search, charts, code execution):

1. **`check_availability`** — reads open slots from `availability` +
   `appointments` tables.
2. **`request_appointment`** — books a slot with name + contact + visit reason
   (the minimum needed to book; the chat states this info is collected for
   booking). Appointments land as *requests*; staff confirm in the admin panel.
3. **`take_message`** — structured message for staff (callbacks, billing
   questions, prescription refills). Billing flow: answer generic policy
   questions via FAQ, then take a message for specifics.
4. **`faq_lookup`** — existing RAG tool over office documents (hours, insurance
   accepted, prep instructions, parking, billing policies).

### Triage guardrail

Not left to free tool choice: system-prompt rules plus a lightweight
urgent-keyword check ensure emergency symptom descriptions always produce
"call 911 / urgent line" messaging and an urgent-flagged staff message.
The agent never triages medically beyond this escalation.

## Channels

- **Web chat:** template's built-in Next.js chat UI, unchanged flow.
- **WhatsApp:** new FastAPI webhook route for the Meta WhatsApp Cloud API
  (GET verification + inbound message POSTs, signature verification), mapping
  WhatsApp conversations onto the same conversation/agent service, plus an
  outbound send-message client. Same no-PHI policy.

## Staff side (admin panel)

- Appointment requests: confirm / decline.
- Message inbox with urgent-flag highlighting.
- Availability management (recurring weekly hours + exceptions).
- Staff-role gate on these routes.

## Data

New tables via the template's repository + service pattern and Alembic
migrations:

- `availability` — staff-managed open hours/slots.
- `appointments` — requested/confirmed/declined/cancelled, with name, contact,
  visit reason, slot.
- `staff_messages` — structured messages with category and urgent flag.

FAQ content is authored as documents and ingested through the existing RAG CLI.

## Testing

TDD throughout (global rules): unit tests for tools/services with mocked LLM,
integration tests for the WhatsApp webhook and booking flow, one E2E happy path
(chat → check availability → book → appears in admin), ≥80% coverage.

## Compliance note

A true HIPAA deployment requires a BAA with the LLM provider and hosting
vendor. The no-PHI-in-chat scope minimizes exposure, but booking names/contacts
still get encrypted-at-rest treatment (standard Postgres deployment practice).

## Task phases

- **Phase 0 — Generate & baseline:** generate project, boot backend/frontend/DB, run migrations, smoke-test stock chat.
- **Phase 1 — Data layer:** models + migrations + repositories + services for the three tables (tests first).
- **Phase 2 — Agent:** receptionist prompt, four tools, remove unneeded template tools, urgent-symptom guardrail.
- **Phase 3 — Knowledge base:** author FAQ docs, ingest via RAG CLI, verify retrieval.
- **Phase 4 — Staff admin:** API endpoints + UI pages for appointments, availability, message inbox.
- **Phase 5 — WhatsApp:** webhook route, outbound sender, formatting, rate limiting, mocked-API integration tests.
- **Phase 6 — Hardening & ship:** security review, E2E test, coverage/lint/type checks, README + deployment notes.
